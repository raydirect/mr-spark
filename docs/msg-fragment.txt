fix: a fragment is not a page, and long rule ids no longer collide

A user pasted one component's markup (a listbox excerpt) and was told their page
had no title and no language. Both findings were about the surrounding document,
which was never in the input. That is the same dishonesty as counting an
unmeasured pillar as zero, applied to input shape.

1. The IR records provenance.kind: 'document' or 'fragment'. A fragment is
   detected conservatively - only an explicit <!doctype> or <html> makes an input
   a document. Rules that describe a DOCUMENT (document-title, html-has-lang,
   bypass) still run on a fragment but are reclassified as undecided, with a
   reason that says why. They are not deleted: the check ran, the answer simply
   is not about this input.

   Consequence: the same snippet scores 89, not 73 - one real finding
   (aria-input-field-name) instead of one real and two spurious.

2. Both surfaces say so, before the score: "this input is a fragment, not a whole
   page - checks about the document (title, language, skip link) are undecided
   here". A fragment score read as a page score is worse than no score.

3. Column collision, visible in the user's terminal: rule ids reach 21 characters
   (aria-valid-attr-value) and padEnd does not truncate, so long ids ran into the
   impact column and produced "aria-valid-attr-valuecritical". Values are now
   fitted: padded when short, ellipsised when long.

4. Unmeasured pillars printed "not measured in this build - not measured in this
   build", because the view model substituted the label and the HTML report
   prefixed it with its own. The summary is now empty for an unmeasured pillar.

5. A fragment's document-level checks carried the environment excuse ("needs a
   rendering surface"), which was wrong for them. They now carry their own
   reason.

fixtures/fragment.html is the user's case, reduced to the essentials, so the
regression is tested rather than described. Tests 59 (was 57).
